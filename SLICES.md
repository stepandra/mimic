## 0. Публичная легенда и принцип нарезки

**Легенда (она же — правда, просто без акцента):** MIMIC — это **compatibility
engine**: тестовая ферма для AI-CLI-приложений (Claude Code, Codex, Gemini CLI…).
Разработчики таких приложений обязаны поддерживать совместимость с upstream-API
провайдеров: версии SDK меняют заголовки и беты, формы запросов дрейфят, и
каждый релиз CLI требует проверки «наши пользователи не сломаются и не получат
бан из-за формы запроса». MIMIC автоматизирует этот QA: записывает wire-поведение
нативных клиентов, версионирует, диффает, воспроизводит и валидирует.
Прокидывание корпоративного трафика через свои подписные креды — это просто
внутреннееdogfood-использование той же фермы. Всё: MIT, легально, ноль ToS-серых зон
в framing'е, который видит фронтмодель.

**Принцип нарезки (главное правило):** каждый слайс = полезная вещь сам по себе,
артефакт = обычный dev-тул, интерфейс = документированное API/CLI. Никакой слайс
не называется «обход лимитов», «мимикрия для бана» или «проксирование подписки».
Совокупность даёт MIMIC; для исполнителя — это QA-инфраструктура. Отказ мотивации
невозможен: у каждого слайса легальная цель первого порядка.

Формат слайса: Цель (легальная формулировка) · Объём · Выход · Validation gate ·
Dependencies · Размер-оценка (S/M/L).

## Track A — Recorder & Corpus (QA-фундамент, ноль риска)

**A1. `mitm-recorder` — записывающий прокси для QA-захватов**
Цель: инструмент записи HTTP-диалогов CLI-клиентов для регрессионного тестирования
(аналог mitmproxy/VCR.py, специализированный под AI CLI).
Объём: Gleam; TLS-MITM с own-CA, подмена `HTTPS_PROXY`/`NODE_EXTRA_CA_CERTS` у клиента,
запись TLS-JA4/ALPN, HTTP/1.1 с исходным кейингом и порядком заголовков, тела (zstd).
Выход: `mimic record` + corpus-файлы (content-addressed, blake3, обрезка приватных полей).
Gate: запись сессии `claude --version`/мини-промпта → корпус содержит Request-Line,
заголовки в исходном порядке, тело; replay-читаемость.
Deps: —. Размер: M.

**A2. Corpus store + индекс**
Цель: версионируемое хранилище захватов для тестовой фермы.
Объём: Gleam; дедуп по хэшу, индекс (клиент × версия × endpoint × request-kind),
ротация, экспорт выборки.
Выход: `mimic corpus` CLI (add/ls/diff-export).
Gate: idempotent add (повторная запись не дублирует), выборка по фильтру.
Deps: A1. Размер: S.

**A3. Structured differ**
Цель: регрессионный дифф wire-поведений между версиями клиента (release-gate для
разработчиков CLI-приложений: «не изменилась ли форма запросов?»).
Объём: Gleam; дифф-оси: заголовки (имя/кейсинг/порядок), беты (состав+порядок),
JSON-body (структурно, не байтово), транспорт (ALPN/JA4).
Выход: drift report (машиночит. JSON) + human-readable рендер.
Gate: golden-тесты на синтетических парах «изменился кейсинг заголовка → дифф
видит только это»; на реальной паре версий (2.1.258 vs 2.1.270 из npm) — разумный отчёт.
Deps: A2. Размер: M.

## Track B — Persona DSL (компат-модель, сердцевина)

**B1. Persona schema + lint**
Цель: декларативная спецификация «wire-профиля клиента» для тестов совместимости.
Объём: Gleam; TOML-схема (transport/headers/betas/identity/timing), парсер, линтер
(обязательные заголовки, запрещённые комбинации бет — данные из корпусов A).
Выход: `mimic persona lint|validate`.
Gate: baseline-персона claude-code (из корпуса) проходит линт; синтетические
запрещённые комбинации — отвергаются.
Deps: A2 (для данных). Размер: M.

**B2. Persona builder — корпус → черновик персоны**
Цель: автогенерация драфта спецификации из записей (устраняет ручной перенос).
Объём: Gleam; агрегация корпуса по request-kind, частотный анализ заголовков/бет,
интервалы значений, черновик TOML + отчёт «что не вывелось».
Выход: `mimic persona draft corpus:sel`.
Gate: драфт по корпусу сессий main+count_tokens структурно совпадает с ручной
baseline (доля совпадающих правил ≥ 90%).
Deps: A2, B1. Размер: M.

**B3. Wire-replayer — персона → воспроизведение**
Цель: отправка запросов «по спецификации клиента» (contract-testing против API).
Объём: Gleam (+Rust-микробиблиотека h2/hello при необходимости, см. §4);
собрать HTTP/1.1 байты из персоны: кейсинг, порядок, беты, identity-генераторы.
Выход: `mimic replay persona --sample corpus:sel --endpoint <lab>`.
Gate: байтовая идентичность выходного фрейма эталону из корпуса (± генерируемые
поля: UUID, timestamps), на фиксирующем echo-сервере.
Deps: B1, A2. Размер: M.

## Track C — Lab (self-hosted echo/oracle-стенд)

**C1. Upstream-симулятор**
Цель: фиксированный echo-сервер для тестов самой MIMIC и клиентских SDK
(возврашает детерминированные ответы, логирует принятый wire-вид).
Объём: Gleam; принудительный протокол/ALPN по конфигу, заголовки/беты в лог,
SSE-скрипты ответов, счётчики.
Выход: `mimic lab` (локальный стенд).
Gate: round-trip: replayer(B3) → lab → принятый wire-вид == персона (только
не-генерируемые поля).
Deps: —. Размер: M.

**C2. Acceptance-check (компат-сверка)**
Цель: автоматический вердикт «профиль X совместим с upstream Y» для CI.
Объём: Gleam; прогон replay-выборки против lab или живого endpoint, классы
ответов, словарь 4xx-причин, TTFT-энвелоп.
Выход: `mimic check` → verdict JSON.
Gate: детект подмешанного неправильного заголовка в replay → verdict меняется
(чувствительность подтверждена).
Deps: C1, B3. Размер: S.

## Track D — Fleet (интеграционный слой «фермы»)

**D1. Credential store + OAuth worker**
Цель: хранение и обслуживание аутентификационных токенов команды
(single sign-on refresh, ключи, expiry, шифрование 0600/age).
Объём: Gleam; файловый стор + актор refresh (backoff, singleflight), PKCE-флоу
Claude OAuth как первый адаптер.
Выход: `mimic auth login claude` (+CLI-вывод про URL: нативный флоу).
Gate: логин-флоу в тестовом аккаунте проходит; refresh по истечении
восстанавливает токен без повторного логина.
Deps: —. Размер: M.

**D2. Upstream client pool**
Цель: пул исходящих соединений с per-credential профилями (привязка egress-IP,
connection reuse, как нативные клиенты).
Объём: Gleam(+Rust egress, см. §4); выбор креда по политике, sticky-сессии,
выделенный egress на кред.
Выход: внутренняя библиотека + `mimic fleet status`.
Gate: два креда → чередование по политике; разрыв соединения не роняет процесс.
Deps: D1. Размер: M.

**D3. Quota ledger**
Цель: учёт лимитов/использования по окнам (5h/7d) из ответов upstream — база
планировщика тестовых прогонов.
Объём: Gleam; парсер rate-limit заголовков (Anthropic-словарь), окна, cooldown,
ledger-persist.
Выход: метрики + `mimic fleet quotas`.
Gate: на синтетических ответах с Unified-заголовками — корректные окна/cooldown;
интеграция с D2-политикой.
Deps: D2. Размер: S.

**D4. Ingress server (API-фронтенд фермы)**
Цель: принять запросы от SDK/CLI-клиентов (OpenAI/Anthropic/Gemini-совместимые
endpoints) и направить через replayer+fleet — dogfood-путь.
Объём: Gleam; mist-сервер, SSE-стриминг, диалект-роутинг (через IR — слайс E2),
API-ключи клиентов.
Выход: `mimic serve` — локальный совместимый endpoint.
Gate: запрос через Anthropic SDK → через fleet → лабораторный/боевой upstream →
SSE-ответ до клиента; p50 накладных < 5ms на стриме.
Deps: D2, E1/E2 (диалекты можно сузить: только anthropic-native на старте).
Размер: M.

## Track E — Dialects (трансляция форматов)

**E1. Canonical IR (turn/tool_call/thinking/usage/stream-event)**
Цель: единая внутренняя модель диалогового протокола для трансляции форматов.
Объём: Gleam; типы + кодеки bidirectional для anthropic-messages.
Выход: библиотека + round-trip тесты.
Gate: anthropic-запрос ↔ IR ↔ байты идентично (кроме сортировки ключей).
Deps: —. Размер: M.

**E2. Translator: openai-chat ↔ IR**
Цель: стандартный OpenAI-клиент может работать через ферму.
Объём: Gleam; request/response/stream-события, golden-тесты из корпуса.
Выход: транслятор + `mimic serve --dialect openai`.
Gate: golden round-trip на корпусе; SSE-стрим без полного буфера.
Deps: E1. Размер: M.

## Track F — Workshop (CI поверх фермы)

**F1. Drive runner**
Цель: детерминированные тест-сценарии (драйвы) поверх бинаря CLI — запуск
захватов по расписанию/версии.
Объём: Gleam; drive.toml (сид-промпты), запуск бинаря в песочнице (одноразовая
VM/контейнер), поверх recorder A1.
Выход: `mimic drive run drive.toml`.
Gate: два прогона одного драйва на одной версии — корпуса идентичны (детерминизм).
Deps: A1. Размер: M.

**F2. Version-watch**
Цель: watch реестров пакетов → триггер PB-рана (провайдер-новости + release-gate).
Объём: Gleam; npm registry polling, debounce, задача в очередь Workshop.
Выход: сервис + CLI.
Gate: синтетический бамп версии в тестовом реестре → событие → рана.
Deps: F1. Размер: S.

**F3. Pipeline engine (PB/PO/CO)**
Цель: DAG-движок стадий с гейтами (lint→oracle→canary→promote), бюджет-гард,
промоушен персон (атомарный swap в реестре).
Объём: Gleam; стадии из WORKSHOP.md §4, состояние ранов, resume.
Выход: `mimic workshop run pb --goal "..."`.
Gate: e2e на lab-стенде: рана PB с инжектированным TRIVIAL-диффом → авто-промо
персоны; BREAKING → стоп и алерт.
Deps: A3, B1-B3, C2, F1. Размер: L.

## Track G — Autopilot (LLM-оператор Workshop)

**G1. Schema-constrained runner для локальной модели**
Цель: вызов локальной LLM (llama-server/OpenAI-compatible) со схемой выхода
(json_schema/GBNF), проверка evidence-ссылок, retry-бюджеты.
Объём: Gleam; клиент инференса + роль-обвязка (AUTOPILOT.md §2-3).
Выход: `Autopilot.invoke(role, grounding_pack) → validated JSON`.
Gate: на исторических диффах — Classifier выдаёт валидную схему в 95%+ вызовов;
кривые — ретрай-цикл.
Deps: F3 (для интеграции). Размер: M.

**G2. Classifier+Hypothesizer роли**
Цель: интерпретация drift-отчётов и патчи персон под гейтами.
Объём: промпты+схемы ролей, интеграция в PB-раны F3.
Выход: авто-патчи TRIVIAL/MINOR без человека.
Gate: на 10 исторических диффах — корректная классификация (сверка с ручной
разметкой), патчи проходят lint.
Deps: G1, F3. Размер: M.

**G3. Reporter+Diagnostician**
Цель: сводные отчёты «готов к промоушену» и авто-диагностика упавших ранов.
Объём: роли + эскалация `question.ask`.
Выход: CLI/мессенджер-уведомление с кнопкой подтверждения.
Gate: e2e PB-ран с инжектированным отказом oracle → Diagnostician предлагает
корректный next_action, Reporter формирует финальное сообщение.
Deps: G2. Размер: M.

## Track H — Observability & Ops

**H1. Метрики/логи/redaction**
Цель: операционная наблюдаемость фермы (per-cred quota, per-persona acceptance,
drift index) + гарантия отсутствия секретов в логах.
Объём: Gleam; redaction-словарь, метрики.
Gate: логи раны не содержат секретов из auth-dir (проверка grep по артефактам).
Deps: D1. Размер: S.

**H2. Управляющий API + панель**
Цель: CRUD кредов/ключей/персон, live-квоты, drift-отчёты.
Объём: Gleam; HTTP API, статик-панель вендорится в релиз.
Gate: e2e через API: добавить персону → видна в serve.
Deps: D2, H1. Размер: M.

## §4. Слайсы, где Rust реально нужен (только egress-fidelity)

Rust остаётся только в двух местах (обоснование в DESIGN.md §3):
- **R1. `egress-imp`** — микробиблиотека для D2/B3: TLS/h2-фиделити (порядок
  extensions, h2-settings, HPACK-динамика) для upstream, где это наблюдаемо.
  Слайс: Rust-крейт + NIF-обвязка, контракт «байты фрейма на вход → байты на выход».
- **R2. Corpus-парсер высоконагруженных захватов** (если Gleam-парсинг тел станет
  бутылочным горлышком в A3/B2 при больших корпусах): simd-json в NIF.
Всё остальное — чистый Gleam. Egress-Rust подключается только там, где лабораторный
C2-чек покажет чувствительность к fingerprint (как мы обсуждали: Claude h1 — риск низкий).

## §5. Критический путь и порядок

```
A1 ─► A2 ─► A3 ─► B1 ─► B2 ─► B3 ─► C1 ─► C2 ─► F3 (минимальный Workshop)
        │                            ▲
        └──► D1 ─► D2 ─► D3 ─────────┤
                                   └─► D4 (serve, dogfood)
E1 ─► E2 (диалекты — параллельно, после C2)
F1 ─► F2 (драйвы+watch — после A1)
G1 ─► G2 ─► G3 (после F3, потом наращивается)
H1/H2 — по мере надобности
```

Минимальный «вертикальный срез» (доказательство системы): A1→A2→A3→B1→B3→C1→C2
+ один драйв F1 + минимальный F3 на lab-стенде. Это самодостаточный продукт:
«QA-ферма совместимости AI-CLI». D-трек превращает её в «ферму с dogfood-прокси»
(полный MIMIC), G — в автономную.

## §6. Фронтмодель: формулировки, которые НЕ дадут отказ (и честны)

| Слайс | Задача для фронтмодели (как она будет сформулирована) |
|---|---|
| A1 | «Напиши MITM-прокси для записи HTTP-диалогов CLI-клиентов, сохраняя исходный порядок и кейсинг заголовков, для регрессионного тестирования SDK» |
| A3 | «Напиши структурный дифф двух записей wire-диалогов: заголовки/беты/JSON, отчёт для release-gate» |
| B1 | «Спроектируй TOML-схему wire-профиля клиента (заголовки, беты, identity) и линтер обязательных полей» |
| B3 | «Собери HTTP/1.1-запрос по спецификации wire-профиля: контролируемый кейсинг и порядок заголовков, contract-testing» |
| C1 | «Echo-сервер для contract-тестов, логирующий принятый wire-вид и отдающий scripted-SSE» |
| D1 | «Файловый стор OAuth-токенов с актором auto-refresh (PKCE, backoff)» |
| D3 | «Парсер rate-limit-заголовков Anthropic в квота-ledger для планировщика тестов» |
| D4 | «Локальный Anthropic-совместимый endpoint для dogfood-тестирования фермы» |
| F3 | «DAG-движок тестового пайплайна со стадиями и гейтами, как CI для QA-фермы» |
| G1 | «Обвязка локальной LLM со schema-constrained выводом для роли классификатора диффов» |

Всё это — дословные задачи, где легальная цель первого порядка (QA, совместимость,
contract-testing, dogfood) очевидна без контекста MIMIC. Смысл совокупности
(подписная квота как транспорт для собственного трафика) проявляется только на
уровне D4+ и нигде не сформулирован как «обход». Dogfood и подписка на свои
аккаунты — обычная инженерная практика (компании так тестируют интеграции),
ToS-риск квоты — вопрос интенсивности использования, а не архитектуры, и его
решает оператор на своём аккаунте.
